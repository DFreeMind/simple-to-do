# 技术架构

## 架构目标

易简清单是 Tauri 桌面应用，而不是独立 Web 产品。架构优先保证本地数据可靠、Windows/macOS 行为可控，以及在没有网络或账号时仍可完成全部核心任务流程。

```text
Vue 3 视图与交互
        │
Pinia 任务状态、派生视图、业务操作
        │
src/services/platform.js（唯一平台边界）
        │
Tauri invoke / 插件 ───────────── Web 开发回退仅用于调试
        │
Rust commands → SQLite、附件、恢复点、窗口、通知
```

## 分层职责

### 前端：Vue 3、Pinia、Vite、SCSS

- 组件负责界面、焦点、弹层和交互反馈；不直接读写本地文件或调用 Tauri 全局对象。
- WebView 内的层级由 `src/assets/styles.scss` 的 `--z-*` token 统一管理：内容 `0`、局部菜单 `20`、局部浮层 `40`、一般遮罩 `1000`、应用内提醒 `1200`、完成页 `1300`、详情抽屉 `1500`、编辑模态 `3000`、确认操作 `3300`。局部菜单必须先提升其父级层叠上下文，不能以更大的子元素数值跨越被遮挡的父级；Rust 创建的原生置顶窗口不使用这套 WebView `z-index`。
- `src/stores/task.js` 负责任务、清单、分组、个人资料、设置、时钟状态、搜索、排序、提醒调度和保存节流。
- `src/services/platform.js` 是唯一的平台封装层：调用 Rust command、读写附件、处理通知权限和非 Tauri 调试回退。
- 富文本使用 Tiptap；结构性图标使用 `lucide-vue-next`；操作音效由 `src/utils/sound.js` 使用 Web Audio API 合成。
- 花种图鉴主舞台使用六阶段透明 WebP 完整盆栽原画。`species-stages/<speciesId>/<stageId>.webp` 保存除小雏菊外 11 种花的完整花盆、盆土和植物，不再拆分花盆层；每个物种的六阶段均从同一张 3×3 成长图集裁切。构建脚本以图集中的空花盆格为唯一基准，六个阶段共享一次缩放与定位，并在源图花盆中心、宽度或底线偏离基准时失败，防止生成会跳动的素材。输出统一为 512×640 透明画布。`FocusStageArtwork` 依据 0–5 连续进度交叉渐隐相邻两张完整盆栽，并在运行时固定盆身遮挡层；天空、太阳、云层、远山和地面仍由 `FocusAchievementWorkspace` 按花种主题及地景构图绘制。小雏菊保留 `FocusPlant` 程序化生长；其他原画加载失败时也回退该组件。阶段跳转由 CSS 完成 680 毫秒渐隐；系统减少动态效果时关闭过渡、柔光和粒子，收藏卡片直接复用同批盛放原画。

### 原生层：Tauri 2 与 Rust

- `load_data` / `save_data`：在前端状态对象与 SQLite 表之间转换，并在写入时剥离附件预览 URL。
- 图片与头像：选择、导入、读取、富文本图片修复和未引用头像清理。
- 数据维护：SQLite 结构检查、迁移备份、本机恢复点、附件扫描、清理站恢复与永久清理；数据保护页可独立检查更新、跳转发布页和打开恢复点目录，不依赖业务数据加载成功。
- 平台行为：窗口关闭策略、托盘/Dock 恢复、系统通知；Windows 的任务与节律通知点击均可恢复窗口，并分别定位任务或打开节律待处理项。Windows 还通过 `GetLastInputInfo` 仅读取汇总空闲秒数，用于连续活跃时长提醒；macOS 当前明确降级为不支持该触发器。
- 原生层不承担产品业务规则；业务规则仍由 Pinia 管理，避免桌面 API 与任务规则耦合。

## 数据与兼容

- 正式版主数据位于 Tauri `app_data_dir()` 下的 `simpletodo.db`；附件、头像、恢复点与数据库处于同一应用数据目录。`tauri dev` 的 debug 构建使用独立的 `cn.duqimeng.simpletodo.dev` 目录，禁止与正式版共用数据。
- SQLite 的 `databaseSchemaVersion` 与前端状态 `schemaVersion` 分开维护。结构变更由 Rust 事务处理；前端状态缺字段由迁移器与 normalize 补齐。
- 数据库读取、健康检查、备份或迁移失败时，应用进入保护状态并阻断写入，不能以默认空数据覆盖现有数据；保护页必须显示已安装版本，并提供更新与恢复点定位入口，不能形成只有“重试”的死路。
- 单独运行 Vite 浏览器页时可使用 localStorage 调试回退，但它不是产品数据路径，也不能代替 Tauri 能力。
- 详细字段见 [数据模型](数据模型.md)，表与文件布局见 [数据库设计](数据库设计.md)。

## 通知、音效与窗口行为

- 提醒由前端维护下一次待投递任务；应用启动、恢复或运行中会检查尚未投递的到期提醒。
- 节律提醒最多三条规则并行启用；Pinia 每 30 秒检查一次，并把最先到期的一条写为 `pending` 后投递，当前待处理项未解决前不会继续弹出下一条。界面以一张主卡显示当前待处理或最近项，并列出随后两项的真实状态；间隔类使用持久化的 `nextDueAt`，不再从旧创建时间猜测下一次提醒。
- 间隔与固定时刻节律会把最近一次截止时间同步给 Rust 原生调度器，避免窗口最小化后 WebView 定时器被节流而漏提醒。到时始终先写入 Pinia 的 `pending`；主窗口聚焦时直接显示应用内处理层，最小化、隐藏或失焦时显示独立全局处理窗，创建失败才回退系统通知。关闭全局窗不会解决提醒，待处理项仍会在回到主应用后继续显示。
- Windows 使用可回调的原生 toast 处理任务与节律通知点击；节律点击会恢复主窗口并切到节律页。macOS 使用通知中心能力，重新激活应用后仍从持久化的 `pending` 状态继续处理。通知权限和系统设置只影响系统通知展示，不影响应用内待处理状态。
- macOS 专注提醒使用现代 `UNUserNotificationCenter`，应用包至少进行 ad-hoc 签名以取得稳定的 Bundle ID 和通知授权记录；不再依赖会吞掉异步发送错误的旧桌面通知路径。设置页提供系统通知设置入口，系统拒绝授权时不得显示“发送成功”。
- 专注与休息开始、暂停、继续或调时时，前端通过 `src/services/platform.js` 同步 Rust 截止调度器。到时由 Rust 检查主窗口的可见、最小化与焦点状态：前台发送 `focus-timer:elapsed` 事件显示应用内完成弹层；后台优先创建跨平台独立完成弹窗，并仍向主窗口发送到时事件完成业务记账。会话 ID 用于取消旧调度和拒绝过期事件，前端墙上时间计算仅作为 Web 调试与异常恢复兜底。
- 后台完成弹窗先隐藏加载，页面读取 Rust 暂存的提醒数据并调用 `focus_reminder_ready` 后，Rust 才真正显示并首次聚焦窗口；窗口默认置顶，`focusReminderAlwaysOnTop` 会随调度参数传到 Rust，并在创建、复用和显示窗口时生效。标题区始终可原生拖动，用户移动后再次提醒沿用当前进程内的位置。三秒内没有收到就绪握手、窗口创建失败或状态不可用时，自动回退到系统通知，不能以“窗口对象已创建”作为投递成功。系统通知点击在 Windows 通过原生 toast 回调恢复并聚焦主窗口；macOS 由通知中心激活应用，并通过 `RunEvent::Reopen` 统一恢复主窗口。
- `focus-controller` 是用户主动打开的桌面控制窗口。Pinia 在开始、暂停、继续、调时和结束时通过 `sync_focus_controller` 同步会话快照；窗口本地根据 `remainingSeconds / elapsedSeconds / syncedAt` 刷新显示，通过事件把暂停、继续、增减 5 分钟和完成操作交回主窗口执行。`focusControllerAlwaysOnTop` 独立保存控制器的置顶偏好，不影响专注完成提醒窗。
- `rhythm-controller` 是所有已开启节律共用的桌面控制窗口。Pinia 仍是唯一业务状态源，通过 `sync_rhythm_controller` 向 Rust 暂存排序后的快照；控制器只依据 `remainingSeconds / syncedAt / counting` 在本地插值显示，全部暂停、单项调时和待处理操作统一通过 `rhythm-controller:action` 交回主窗口执行。窗口默认停靠在当前屏幕右上角：折叠为 `390×86`，展开根据实际渲染的 1–3 项节律使用 `390×228`、`390×324` 或 `390×420`，从顶边向下展开；工具栏始终提供收起入口。
- Rust 负责节律控制器的创建/复用、置顶、隐藏、折叠尺寸和显示器边界。展开时保持窗口右上锚点；与可见的 `focus-controller` 发生物理重叠时优先移动节律控制器。关闭事件只隐藏并清除瞬时展开状态，计时与待处理状态不受影响。
- 控制器保持单一原生窗口和单一业务状态源，Vue 呈现层按 `focusControllerStyle` 在 `orbit / island / classic` 三种组件间切换，不复制计时或操作逻辑。形态值随控制器 payload 同步给原生层；Rust 负责按形态设置逻辑尺寸、保持窗口右上角锚点并限制在当前显示器工作区。专注岛的展开状态只存在于当前窗口运行时，不写入个人数据。
- 控制器窗口统一以透明无边框窗口创建；轨道表盘和专注岛使用透明边缘与 CSS 阴影，经典卡片绘制完整不透明背景。macOS 透明 WebView 依赖 Tauri `macos-private-api`；当前 GitHub DMG 分发可启用该能力，但必须在 macOS 实机构建验证。若未启用或验证失败，macOS 回退到专注岛与经典卡片，不能显示带方形底色的伪圆表盘。
- `ReminderWindowCoordinator` 按窗口角色管理显示关系，而不是让所有窗口互斥：

  | 窗口角色 | 当前实例 | 显示与焦点规则 |
  | --- | --- | --- |
  | 持续工具窗 | `focus-controller`、`rhythm-controller` | 用户打开后持续显示；置顶仅改变系统层级，不参与临时提醒互斥，也不被提醒自动隐藏；两个控制器重叠时节律控制器自动避让 |
  | 临时提醒窗 | `focus-reminder` | 同时最多显示一个并取得焦点；已显示窗口不被抢占，其余进入原生队列 |
  | 系统通知 | 专注完成、任务与节律提醒 | 任务和节律通知用于把用户带回主应用；专注完成提醒作为独立完成弹窗的回退 |

- 临时提醒队列只协调专注完成弹窗，不会覆盖节律待处理项。显示临时提醒前检测它与可见控制器的物理窗口范围，发生遮挡时优先把提醒移到控制器左、右、下或上方的可用区域；控制器首次打开默认位于主屏右上角，之后仍允许用户拖动。
- 操作音效使用 Web Audio 的 oscillator、滤波和包络合成，避免 macOS WKWebView 对 OGG/Vorbis 音频的兼容问题；只为有结果的操作播放。
- 关闭窗口可设置为隐藏到后台或直接退出。隐藏后，Windows 可通过通知区域托盘恢复；macOS 可通过 Dock 或菜单栏恢复。两端应验证等价用户结果，而不是依赖相同 API。

## 发布与更新

- 版本以 `package.json`、`src-tauri/tauri.conf.json` 和 `src-tauri/Cargo.toml` 为准，三者必须一致。
- 正式发布固定通过本地脚本执行：`node scripts/release-local.mjs --version <version> --notes-file <notes.md>` 依次完成构建、创建或更新同一个 `v<version>` GitHub Release、生成无 BOM 的 `latest.json`、同步自建更新源并做线上校验。历史 `release.yml` 不作为正式发布入口，避免多个发布者并发覆盖同一版本的资产或更新清单。
- 资产名固定且架构可辨识：Windows 为 `simple-to-do_<version>_x64-setup.exe`；macOS 手动下载安装包分别为 `simple-to-do_<version>_x64.dmg` 与 `simple-to-do_<version>_aarch64.dmg`。macOS updater 另上传同架构的 `.app.tar.gz` 和 `.sig`，DMG 仅供手动安装，不能替代 updater 包。
- 本地流程先发布 Windows x64；macOS Intel 与 Apple Silicon 构建完成后追加到同一个 Release。发布前必须运行 `npm run release:check -- <version>`，并核对版本、签名私钥、Git 工作区和 `gh` 登录状态；同一版本只允许一个发布者执行。
- CI Secret 必须配置 `TAURI_SIGNING_PRIVATE_KEY`、`TAURI_SIGNING_PRIVATE_KEY_PASSWORD` 和 `DEPLOY_SSH_KEY`；后者仅在同步阶段写入 runner 临时文件，进程结束即删除。`DEPLOY_SSH_HOST`、`DEPLOY_SSH_USER` 可选，默认服务器为 `47.116.185.192` / `root`。
- 更新器使用内置公钥验证更新清单与安装包签名；更新源支持多端点，客户端默认「自动」模式按顺序尝试（自建服务器优先，GitHub 兜底），也可在「设置 → 关于与更新」手动指定自建服务器或 GitHub。某个 Release 没有签名更新清单时，应用必须提示用户到 Release 页面手动下载，而不是宣称在线更新可用。
- 更新器签名密钥：本地 `~/.tauri/simple-to-do-updater-v3.key`（密码见同目录 `simple-to-do-updater-v3.password`），由 `scripts/build-windows.ps1` 注入构建环境，pubkey keyid 为 `403511B997506DCC`。发布后必须核验 `exe.sig` 的 keyid 与 pubkey 一致（`tauri signer sign` 重新签名的产物 keyid 也应一致），否则客户端验签失败、自动更新不可用——0.4.4 首轮 CI 曾因 secret 配置成旧 key（keyid `6955E9F5063ED6F8`）导致全部用户更新失败，后更新 secret 并重跑发布解决。
- 客户端更新行为：主窗口启动后静默检查一次，发现新版本在「设置 → 关于与更新」显示角标，并可在侧边栏设置入口显示红点；用户可以「跳过此版本」（版本号持久化在 `settings.skippedUpdateVersion`），数据保护页检查更新时不受跳过记录影响。
- Windows 使用 NSIS passive 安装模式，安装参数携带 `/R`，安装完成后应用自动重新打开；macOS 只有在同一 Release 同时存在对应架构的 `.app.tar.gz` 与 `.sig` 时才写入 updater 清单，否则应用在更新卡片如实标注并引导到下载页，不显示「已是最新」。
- 自建更新源：`https://simpletodo.duqimeng.cn/releases/`（服务器 `47.116.185.192`，Nginx 站点根目录 `/data/simple-to-do/releases`），固定路径 `latest.json` 为更新清单，版本目录 `<version>/` 存放安装包与签名；站点仅提供 `/releases/` 前缀，旧路径 `/latest.json` 与 `/<version>/` 已移除（返回 404）。客户端检查更新由自定义 command `check_for_update` 动态构建端点（`src-tauri/src/main.rs`），更新包下载安装由 `install_pending_update` 执行并通过 `updater:progress` 事件回传进度；前端 `src/services/updater.js` 不再直接调用插件默认 check，更新源选择持久化在 `settings.updateSource`（auto / github / self）。
- 发布同步：`scripts/sync-update-source.mjs` 按 `latest.json` 下载每个平台的 updater 包和签名，同时下载 macOS DMG，改写清单 URL 到自建服务器后上传并逐个 HTTP 200 验证。服务器连接本地可使用默认 SSH 私钥或 `DEPLOY_SSH_KEY_FILE`。代理说明：更新器依赖的 reqwest 必须启用 `system-proxy` feature（`Cargo.toml` 已声明）才能读取 Windows 系统代理，否则系统代理环境下直连 GitHub 超时会导致检查更新失败。

## 架构边界

不维护 Electron 运行时或独立 Web 版本；不为未上线的账号、同步、协作建立假接口。若未来加入这些能力，必须保持本地 SQLite 可读写、个人资料不依赖登录、数据恢复可用。
